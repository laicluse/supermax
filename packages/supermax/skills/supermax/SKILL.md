# Building on Supermax

Supermax (`@laicluse/supermax`) is an application shell: a `Navigator` decides what is open, a `Workspace` renders it as cells in branching rows and moves them. A host owns its content, its routing and its data, and follows the contract below so that every app moves the same way. This skill guides spatial design and holds the contract and when to use each feature. Signatures and options live in the installed package, so read them there before you call anything:

- `node_modules/@laicluse/supermax/README.md`, section "Workspace reference": every workspace method with all its options.
- `node_modules/@laicluse/supermax/docs/application-shell.md`: the behaviour behind them (window and Show, groups, loading layout, modals, notices, motion, time).
- `node_modules/@laicluse/supermax/docs/folding.md` and `docs/reachability.md`: space trading, recovery routes and their guarantees.
- For a major upgrade, inventory the host's existing contracts and read `docs/migrating-to-v2.md` from the target package or its matching release notes; a v1 install lacks it. Retaining `CellCollection` or `CellStrip` does not require adopting `Workspace`.

When the package is linked from a checkout (`file:`), the same files are in that checkout.

## Understand the spatial model

Read the installed guide's **Vocabulary**, **Start with the cell path**, **Rows** and **The window and Show** before designing the hierarchy. Think in tasks and relationships, then express them as:

```text
root -> collection -> item split                 -> full-height task
                         | source row -> detail     (opened from a row)
                         ` activity row -> event
```

A destination defines content and layout; an occurrence is that destination at a particular path, with its own local state. A chain opens children to the right. A split gives independent branches their own rows and horizontal chains; it opens in the root chain, never inside a row. Rows belong to their split and do not close independently. A full-height destination opened from a row stands beside the split; each split has one such breakout at a time, whose chain may continue to the right.

**Open is not the same as visible.** Allocation hides or folds cells and rows without disposing them; drafts and selection remain. Resize changes the visible window, not the open hierarchy. Show recovers earlier context, including folded content: horizontally it can close visible trailing cells to make room, while vertically it moves the row window. It never discards a subtree containing content that was hidden before the action. Clicking a fold cue trades space with neighbouring content while both remain open. Closing has lifecycle and draft consequences; the host owns protection and history. Read **The window and Show**, **Navigation groups** and **Deep links and browser history** for the precise behavior rather than treating Show as browser Back.

**Reachability belongs to Supermax.** Every open occurrence has a route in `navigator.layout().access`: allocated content (possibly reached by scrolling), a next fold page, Back/Show, or zoom-out. The allocator refuses a layout without a route. This is a model guarantee, not proof that host CSS, focus handling or an arbitrarily tiny viewport leaves controls usable. If an open cell has no working recovery control, check host CSS and event interference, then reproduce any remaining shell defect; do not compensate with host hiding, duplicate navigation or automatic closure. Never mutate the access map or navigator selections to steer allocation.

## Compose around the user's work

For a new shell or an adaptation, produce the design proposal yourself from existing task analyses, design decisions, routes, code, real content and captures. Read the project's design research before reducing its intent to today's implementation. Distinguish observed behavior, accepted decisions, exploratory proposals and assumptions; verify their date and current relevance. Captures establish visible presentation, not frequency, scope or hidden behavior. Follow the guide's **Adaptation checklist** for implementation coverage; when upgrading existing Supermax contracts, also use the target package's migration guide.

### Inventory and choose

Map reachable tasks and their information and controls, including reading, comparison, creation, editing, drafts and recovery. Record ownership and scope, importance, frequency, data density, required simultaneous context, selection, focus and scroll ownership. For a complex app, inventory everything but walk representative tasks through the hierarchy; include a cross-component comparison and an interrupted edit. A route or component inventory is not a requirement to open everything together. Include existing tabs, parallel work contexts and separate mobile shells: decide how they retain identity, drafts and access when mapped to occurrences. Separate three relationships: domain ownership, navigation ancestry and simultaneous work. Related data need not be parent and child; peers with shared selection or synchronized pan/zoom need not become a navigation chain. Distinguish a destination type, the record it shows and each occurrence of it: the same record can appear in independent work contexts while sharing data updates. Bulk selection is a set to act on, not a demand to open one cell per record. Establish cold-start selection from the task; read **Cold start** instead of inventing an arbitrary first item.

Start with familiar UX patterns and explain their task benefit before mapping them to cells and rows. The following examples are an open vocabulary, neither exhaustive nor mutually exclusive: use other patterns, combinations or justified variations when they fit. A recognizable name does not replace an explanation of the behavior needed.

| Pattern example | Relationship to preserve | Possible Supermax expression |
| --- | --- | --- |
| List-detail (master-detail) | Selection with collection context | Collection → item chain |
| Overview + detail | Consult the whole while investigating a part | Overview beside detail, when both fit |
| Supporting pane / inspector | Context belonging to the current work | Contextual child; independent row when its task warrants one |
| Split view | Related surfaces with independent selection and scroll | Stacked rows or neighboring full-height cells |
| Progressive disclosure | Secondary information available on demand | Navigation or reading disclosure; optional context through `ifRoom` |
| Coordinated comparison | Compare peers using shared controls or a common axis | A compound task surface, or independent cells when their navigation is genuinely independent |
| Document workspace | Read sources while producing substantial work | Source context beside a full-height editor |

Compare at least two plausible compositions, including both horizontal and vertical opportunities. Inspect embedded cards, footers, status strips and side panels for independent tasks. A split earns its height through useful simultaneous context and independent selection, scroll or navigation; filters and actions on one surface usually stay with that surface. Consider full-height work beside a split when a row cannot provide useful reading or editing space. Preserve a single chain when splitting adds cost without task benefit.

Recommend one composition and its main trade-off. Show alternatives when an unresolved consequential choice needs discussion; do not make the operator perform the inventory or choose from a catalog. Explain which familiar expectations carry over, what Supermax changes, and what happens when required context no longer fits. A missing capability or loss of simultaneous comparison must be explicit, not hidden behind an attractive diagram. Map each required relationship to native shell behavior, a compound task surface inside a cell, or a capability gap to resolve. A useful component, grid tile or data dependency is not automatically a destination. Use host layout for a cell's own task content; do not invent ancestry to simulate arbitrary nested splits or use content layout to replace the shell's navigation.

### Allocate space and controls

Treat allocation as a task policy, not a collection of attractive pixel values. For each surface, explain what the user must still be able to read, decide or operate when space is scarce, which context may leave view, and the action that recovers it. Required simultaneous evidence must remain usable together; access through Show is sufficient only when alternating actually supports the task. Preserve identity, consequential state, essential actions and draft recovery without keeping every surrounding panel visible. Consider task frequency, interruption cost and whether hidden background activity needs scoped feedback.

Derive bounds from real content at the cell's allocated size, after chrome, rather than from viewport labels:

- **Minimum:** the smallest size at which the task still works, with readable content, usable controls and a viable scroll region. Lowering it just to fit more cells conceals a design failure.
- **Preferred:** a useful working size for the common task and content, not a screenshot's dimensions. Check both typical and dense states.
- **Maximum:** where extra room stops helping this content. Assign elastic growth to work that benefits from it; use the guide's **Widths express content semantics** for exact allocation rules.

Width and height have separate budgets. At narrow widths, reason through the actual ancestor-hiding order, kept content at its declared minimum, optional `ifRoom` openings, and full-height work beside a split. `overflow.mode: "keep"` must earn its space; keeping everything can force overflow. A kept cell must remain usable at its minimum, and an optional pane must have an explicit opening path when it did not open automatically. Specify what remains open but hidden, rather than describing all disappearance as closure.

For height, `minViewportHeight` guarantees that each split can show one row at its minimum with its chrome; it does not require all rows to fit simultaneously. Rows fold by default. Excluding one with `overflow: { mode: "hide" }` allows it to leave the row window without a fold handle. Give the elastic row useful growth and verify each row through its recovery route, divider extremes and scrolling. Below the declared height, folding may still fit the task; `layout.overflow` reports actual overflow. Do not add a “viewport too small” warning for a layout folding can solve. If the active content itself cannot fit, preserve scrolling and address unusable bounds or controls.

Cell and row minima must be finite and positive; finite maxima cannot be below them. Every elastic cell or row needs a finite preferred size at or above its minimum. An optional preference under a finite maximum must stay within those bounds. Validation errors require correcting declarations, not shrinking content with CSS. Use ordered `variants` when content changes appearance under pressure and the smaller form needs less room. Give each form its own useful bounds: an icon menu normally caps its width at its minimum instead of retaining the label form's preferred/max width. A separate admission condition determines when the richer form fits. Supermax selects the form per occurrence across both axes, emits its ID, and gives released space to useful neighbours; the host styles `data-variant` or `data-row-variant`. Treat vertical variants as a first-class space-saving choice on mobile: a large context block can become a compact summary strip, preserving selection, meaningful status and essential actions while the work row receives the released height. Declare those forms on the split row with its own height bounds; styling a cell alone does not shrink its row. Cap a fixed-height summary at its useful minimum, and use `overflow.mode: "keep"` only when it must remain visible. A compact form is allocated content, not a fold. Test short heights, including an on-screen keyboard, as well as narrow widths. Vertical and horizontal form changes share the same managed animation lifecycle. Follow README's **Responsive variants** reference for declarations and explicit content-driven updates; do not use rendered dimensions or animation frames to mutate space requests. Supermax never measures content: when a form's size should follow its content, compute it from content inputs (lines, items, a known font), declare one content-derived form plus a compact fallback, and call `setVariants` again when the content changes. Within a row's declared bounds, `setSize(row, height, "height")` sets a computed height without forms. Never copy pixel sizes from a render into fixed forms or stack forms that differ only in height. Ordinary content may still reflow within its chosen form.

Place controls by scope and frequency using **Cell anatomy** and **Control, modal or cell** below. Keep collection filters at the top of their collection, repeated task actions with the task, and independent choices accessible. The `header` handle mounts a small set of useful utilities; it is not a toolbar checklist. Title bars are optional, in rows as well. Verify actual control placement, long titles and narrow widths instead of adding helper text to explain an ambiguous grouping.

### Show the proposal while building

Before layout implementation, show compact ASCII region maps labeled with task names, row boundaries, navigation direction, active selection, scroll owners and full-height breakouts. Cover wide/narrow widths crossed with short/tall heights at measured or explicitly proposed CSS viewport dimensions. Use the same open state across these maps to isolate allocation; show a separate map when an action changes that state. Annotate what stays visible, folds, hides while open, opens optionally or closes, and how it is recovered. Update the maps when the proposal changes.

The maps describe one hierarchy. Verify the proposed states against the documented window behavior: `ifRoom` opens on navigation, never resize alone; ordinary space allocation keeps a kept cell at its declared minimum; ordinary cells and rows fold by default, `overflow: { mode: "hide" }` excludes a surface, and `overflow: { mode: "fold", size }` optionally reserves space. Do not implement a sketch through host CSS hiding, responsive reparenting or automatic closing. [Composition exercises](composition-exercises.md) provide optional task probes, not layouts to copy.

## Control, modal or cell

Use the installed application-shell guide's "Controls, modals and task cells" for the complete rule and sources. Decide by task length, frequency, risk, recoverability and need for context, never by an HTML form, field count or existing presentation:

- **Control in place:** direct actions and compact contextual inputs stay where the task happens; feedback is proportional and confirmation is reserved for risk that justifies interrupting. Easily reversible toggles need none.
- **Modal:** a short, bounded, infrequent task that benefits from blocking; use `openModal` with its source `from`.
- **Cell:** substantial editing, steps, drafts, detail or comparison; a task that needs surrounding content must not block it in a modal. Content that needs the full height, such as an attachment listed in a row, is a cell declared `placement: "beside-split"`, not a modal and not a cell squeezed into the row.
- **Disclosure:** extra reading information, without unfolding a new editor between reading content.

Preserve choices, defaults, pending/result feedback, errors and recovery when moving an interaction. The host owns focus entry, return and modal containment; Supermax moves no focus itself.

## The contract per click

1. **Pass the clicked element as `origin`** to each click-driven `navigate`, `sync` and `depart`; for `apply`, put `origin` in the open action, not the options. A replaced cell folds away towards the new click, compared with the click that opened it; without an origin it folds on its far edge. Pass `origin: null` when nothing was clicked (a route change, a keyboard shortcut, a timer).
2. **Pass `from` to `openModal`**: the occurrence the modal belongs to, so a frustum links them. `from: null` for a modal that belongs to no cell.
3. **Know the layout before you open.** A split declares `rows` instead of width; its width follows what is open in its rows. Every destination the page does not embed needs its layout declaration registered first: `navigator.register(await readLayout(response))`, from a `HEAD` the server answers with a `Supermax-Layout` header.
   - Prefetch it when a pointer rests on a link for about 100 ms.
   - Keep one in-flight promise per destination and viewer context; a click waits on that same promise instead of sending a second request.
   - A deep link or reload asks for every layout it needs in one batch, then renders once without motion.
4. **While the layout is on its way, call `depart`**, so the cells the click replaces fold away in their rooms instead of nothing happening. When every declaration is already known, skip `depart` and call `sync` (or `navigate`) at once. When the layout fails, call `cancel()` on the handle `depart` returned. Offer a Retry only for a failure that can pass, a network error or a 5xx; a declaration that `register` refuses (`SupermaxConfigurationError`, for example a `context` that differs from the navigator's) fails the same way every time, so log it as the host bug it is.
5. **One render per click.** Use `sync` when the host owns the destination chain, or `navigate` for an opening from content. With `onIntent`, the host commits that intent through `apply`; do not also sync the same action. Never call `sync`, `navigate` or `render` from a `render` or `zoom` event handler; react to the event without rendering again.

The workspace warns once per kind in the console when a host leaves out an `origin` for a replacement or a departure, a `from` for a modal, or renders from a render handler. Treat such a warning as a bug in the host.

## Choose the implementation feature

### Navigation and available space

- **`sync(destinations, { origin, ifRoom })`**: the host knows the whole chain, for example from its URL. One call per navigation; it keeps what is shared and renders once. After a split the next id names one of its rows and the chain continues inside it, so a cell inside a row that the URL names is synced, not navigated to in a second render.
- **Active menu item**: read `navigator.focus()` and listen to the workspace's `focus` event instead of deriving the state from the host's own chain. Declare `menu: true` on each destination with a menu item, or `menu: "exact"` for a starting point such as an agenda whose item should go dark once the user works in a record it opened, and mark `focus().menu`. Do not match `destinations` against the menu in the host.
- **`ifRoom`**: a cell that should open only when the window has room for it, such as a detail pane next to a list. It is an ordered chain; the longest beginning that fits without hiding a cell in view opens, as automatic cells that a later explicit sync or click promotes, and that a later sync without them in its `ifRoom` closes. It never opens on resize. Cells that only make sense together, such as a conversation's metadata and its messages, go in as one nested list, `ifRoom: [["metadata:1", "messages:1"]]`, so they open whole or not at all.
- **`navigate(destination, { from, origin })`**: a click inside a cell's content that opens something to its right, or beside the split when the destination declares `placement: "beside-split"` and the click came from a row, when the host does not keep the chain itself.
- **The `show` event**: cancelable before Show closes cells; prevent it to keep an unsaved form open. It guards Show only: browser history, tab switching and other navigation need the host's own draft protection or persistence. The `up` event names the closed cells in `detail.closed`, with destinations, so the host can record the step in its history.
- **`zoom(occurrence)`**: a cell that should take the width of the cells before it, for a destination declared `zoomable: true`. Draw the toggle in the content's `header`. Show always exits zoom first, even when no ancestor immediately returns; its accessible name is then `strings.zoomOut`. Zoom and fold focus do not compete for the active surface. When a sync replaces the zoomed cell, for example after archiving it, pass `zoom` with the destination that stays zoomed, so the cells before it never flash into view.
- **`placement: "beside-split"` on a destination**: content that needs the full height, such as an attachment opened from the attachments row of a conversation. From a cell in a row it opens beside the split instead of inside the row, keeps that cell as its origin (`navigate(destination, { from: rowCell, origin })`), and one such cell stands beside a split at a time. A deep link that ends in it is one `sync` whose destinations run through the split, its row and the row cell to the beside-split destination, the occurrence's own path; `navigator.next(split)` names the cell beside a split.
- **Kept cell**: a menu or other surface that should stay visible when ordinary space allocation runs short. Declare `overflow: { mode: "keep" }` and choose the smallest `min` at which the host's own responsive content works. Zoom is an explicit exception: it can hide kept cells before its target, with Show available to exit zoom. Do not treat `overflow.mode: "keep"` as permanent viewport chrome.
- **Folding**: ordinary cells and rows fold by default; `overflow: { mode: "hide" }` opts an important surface out, and `overflow: { mode: "fold", size }` optionally reserves space on that surface's axis (0px by default); `size` is valid only for `mode: "fold"`. `overflow.mode: "keep"` preserves visibility at the minimum during ordinary allocation; `overflow: { mode: "hide" }` alone does not. Each horizontal chain and vertical split keeps its own choice. A fold click asks to see that content and trades space without closing either side; Show goes toward earlier context and never toggles the fold back.
- **Fold interaction**: only the fold handle opens a fold; the bare gutter does not. Consecutive folded pages expose the nearest page, then the next, like a book; do not expect a handle for every hidden occurrence at once. Earlier pages also remain available through Show. Mouse and touch dragging share the directional 61.8% threshold: past it commits, otherwise returns; release animates the remainder. Initially visible handles remain during a drag, with only the dragged one active. On touch/coarse pointers, fold and resize-reset controls have minimum 44 × 44 CSS-pixel hit areas; the reset minimum also applies to fine pointers. `renderer.fold` customizes the cue's contents; the shell owns positioning, hit areas and gestures.
- **`layout.chains.get(root).spare`** (from the `render` event or `findChain`): the width a chain leaves unused, for a host that fills free space with something other than a cell.

### Content and identity

- **Content handle `{ element, header?, update?, transition?, leave?, dispose? }`**:
  - `header`: the content's own lightweight utilities in the cell's title bar when it has one, otherwise at the start of its body; choose their scope and placement as above;
  - `update`: refresh after every render;
  - `leave()`: stop writing shared state the moment a cell starts to close, because it stays mounted while it folds away;
  - `dispose()`: clean up once it is gone.
- **`header: "title"` on a destination**: the exception, not the rule. A cell has no title bar; declare `header: "title"` only for a cell a viewer cannot place from its content, such as a list of edit names or a cell with one control. A cell inside a split row may declare it too and draws its bar within the row's height. Name a thing once: when the split's bar or the content already shows a name, a row cell bar or an `<h2>` that repeats it is noise. A strip of thumbnails, a map, a photo, a conversation's messages under the split's own bar need none; a title bar on every cell wastes a line and a glance each. Use `renderer.header` to draw the bar while keeping its supplied navigation action and utilities outlet; do not hide or add structural title bars.
- **Application state**: Supermax holds no application data and no store, and it lets cells share nothing. One store in the host above the `content` callbacks, however large, is fine and usually right: each cell renders a view on it, so a record that two cells show loads once. Pass ids in a destination's `data`, not loaded records. Mounting one component in two cells risks two loads and two sets of key handlers. Split along the task instead, and let each cell render its own part from the shared store.
- **Titles**: a cell's title names the content the cell shows, such as the vault's name, a conversation's subject or "3 open todos", never its role in the structure, such as "Viewer", "Detail" or "List". The host supplies it; declare it with the content's name, and use `setTitle(occurrence, title)` when that name or a count is known or changes after the cell opened.

### Feedback and presentation

- **`openModal`**: the modal in "Control, modal or cell" above, opened with `from` set to the cell it is about.
- **Shared notices**: `notify` is the shell's toast or flash message. Use it for temporary feedback and persistent interactive recovery, rather than a separate host banner. Scope a cell result to its occurrence through `source`; use workspace scope for an app-wide condition. A hidden source moves its notice to the shared stack with a Show route; a closed source is not reopened by a late result. An active stable `id` prevents duplicate notices; update it with `updateNotice`.
- **Notice lifecycle**: temporary notices expire after 7 seconds by default, with expiry paused while hovered or busy. Success is temporary; error and action notices are persistent by default. Set `persistent` explicitly when the task needs another lifecycle. An action's returned Promise drives the busy spinner and prevents duplicate execution. A temporary notice closes on successful completion; a persistent one waits for host dismissal. Rejection clears busy state and re-enables the action; the host supplies meaningful error feedback. For event-driven work, update `busy` explicitly. Call `dismiss(id, "resolved")` when the underlying condition clears, not merely when a request was accepted. User dismissal is distinct from business resolution; do not reopen the same incident on every status poll. Use `dismissAll` when resetting the host context. Read the notice reference for signatures and events; this is a message/action API, not an arbitrary form container.
- **Loading**: a Promise returned by `content` uses the built-in centered indeterminate ring, with an accessible loading name and no visible loading sentence. Do not add a second spinner or “Loading …” label. Failure gets the cell's Retry state; a separate notice is not automatic.
- **Variant transitions**: use the content handle's `transition` participant when host content should animate a form change. Capture drawn values before cancellation, prepare the final content, and register effects through the supplied `animate` function. This joins the existing presentation timing, retargeting, fold-drag seeking and completion; never add a parallel scheduler. See README for the hook signature.
- **Presentation**: `VEIL_PRESENTATION` is the default, suitable for large or complex content. `ORIGAMI_PRESENTATION` is the other built-in export; Paper Fold is a custom-presentation example in the demo, not an importable preset. Fold transitions and resize resets belong to the chosen presentation and shared timing; content must not reflow through intermediate animation widths. Exercise reversal, interruption, touch cancellation and reduced motion rather than adding host transitions.
- **Host rendering**: use the workspace's `renderer` map for visible shell parts, including canvas, cell material, headers, navigation, fold cues, divider/reset controls, loading/errors, notices, modals/backdrops, veil and frustum. `DEFAULT_RENDERER` is the complete default. Factories mount once and return optional `update`/`dispose` handles (`paint` for frustum geometry); never remount product content or start a host animation clock. Bind host native buttons to the supplied actions and retain required outlets. Geometry, clipping, recovery, semantics and all transition timelines remain Supermax-owned. Read `docs/rendering.md` for signatures and the complete catalog; use public roots/outlets instead of private selectors. Default paint tokens use `--supermax-default-*` and belong to that renderer only; set `--supermax-default-canvas` for the canvas and `--supermax-default-surface` for cell backgrounds. Pass `chrome: { header }` to the `Navigator` once for title-bar height. A gutter is a transparent skin break; keep room boundaries intact. Use `frustum() {}` to omit the drawing. Frustum factories paint stable shell-computed faces; the shell owns growth and source tracking. Navigation's clicked-element `origin` remains a separate method input.
- **`TimeScale`**: one scale for every millisecond. Pass one `time` to every workspace, scale the host's own waits with `time.ms(milliseconds)`, and write the host's own CSS durations with `time.paint(element, { times, easings, prefix })`.

## What a host never does

- **Call internal methods** such as `navigator.fits`, `openIfRoom`, `openDefaults` or the strip's methods. Use the documented route (`sync` with `ifRoom`); if none exists, ask for one in Supermax instead of reaching inside.
- **Recreate modal mechanics**, or move controls into private `.supermax-*` elements after mount. Use `openModal`, `renderer.modal` for its appearance and the content's `header` outlet for utilities.
- **Label a source next to the frustum** ("From …"). The frustum shows it, and the dialog describes it to assistive technology.
- **Imitate gutters with product-content borders or margins.** Render materials inside their supplied roots; let the shell expose the canvas between cells. Do not paint over its gaps or resize targets.
- **Animate cells, rooms, rows or the strip itself**, with CSS transitions or Web Animations on `.supermax-cell`, `.supermax-room`, `.supermax-row` or `.supermax-strip`. Motion belongs to the presentation; a host that needs different motion supplies a `presentation`, such as `VEIL_PRESENTATION` when its cells are large enough that origami's fold moves a screen of content.
- **Rely on `position: fixed` inside cell content.** Cells and the strip carry transforms, so a fixed element positions against them, not the viewport. Move a popover to `document.body` or into the overlay root.
- **Repeat a signature in its own docs or instruction files.** Point at the package docs above, so an upgrade cannot leave a stale copy behind.

## Integrate an existing application

When upgrading existing Supermax contracts, use the target package's migration guide for the implementation sequence. Preserve the product's task coverage as well as its geometry:

- Bind each mounted cell to its own destination and occurrence context, not a global current route that changes underneath it. Carry framework providers, stores and event cleanup into independently mounted roots. Separate shared record updates from local selection, scroll and drafts; restore those deliberately across workspace/tab switches. A navigation snapshot does not store application data. Use `workspace.restore` to restore it; stale zoom, fold and window references are discarded, while unknown destinations refuse restoration. Do not hand-edit snapshot internals.
- Identify actions that create, start, submit or otherwise mutate work. Mounting, prefetching, optional opening and history restoration must not accidentally repeat them. The same click can mean navigation or an in-place action depending on the current mode; preserve that distinction.
- Plan required declarations, initial selection, optional groups and zoom before the navigation commit. Late data must not cause a second automatic navigation for the same intent. Cancel superseded departures and disregard stale results; an optional load failure must not strand required work. Update loaded titles and content without rebuilding the workspace or replaying navigation.
- Keep server and embedded/offline declarations consistent with the same source. Verify the installed package and the served JS/CSS or standalone output; a local dependency can be a snapshot. Rebuilding a source checkout alone does not update consumers.

Walk one complete task through entry, work, interruption and recovery, then cover the remaining routes and control outcomes. Do not weaken an existing required guard to fit a primitive: verify the current modal and navigation limits before replacing it. Fix integration through public contracts rather than copying internal shell behavior.

## Verify the adaptation in use

Measure the viewport and workspace after application chrome. Inspect the render with realistic long labels, dense/empty/error content and active drafts at the proposed dimensions and where content ceases to fit. Run the guide's **Adaptation checklist** interaction checks: deep links, reload, browser history, Show, hidden rows, selection continuity and control scope. Test optional openings and full-height work from their actual origins. At each size, actually finish the task with the proposed minimums: inspect hidden essential controls, lost comparison context, excessive scrolling and unreachable recovery. Try repeated records in separate contexts, coordinated peers, bulk selection and mode-dependent actions where the product has them; these are probes of responsibility, not a required screen catalog.

For every open occurrence, actually follow its fold pages or Show route until the content can be operated. Test several folded rows, independent horizontal folds inside them, both drag directions and release on either side of the threshold. Check one canvas gap per boundary throughout motion, handles attached to that gap, no lost controls, and no content reflow. Exercise temporary notice expiry, persistent dismissal, Promise busy/failure/retry and host-driven resolution, including while its source is hidden or closed.

Exercise keyboard reading order, accessible names, focus entry/return, visible focus, usable targets and browser/text zoom. The host owns focus. Hiding, Show and closing are different transitions: check scroll, selection and drafts through each. Short height must leave the active task and recovery usable; optional context must remain discoverable. Protect expert density, stable positions and direct access during repeated use.

Report expected versus observed allocation and behavior, fix mismatches, and refresh the maps and captures. A diagram, passing allocator test or model review is not evidence of a usable rendered application. If the runtime is unavailable, deliver a clearly labeled proposal with its unresolved checks.
